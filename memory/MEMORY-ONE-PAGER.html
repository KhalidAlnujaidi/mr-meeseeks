Remember the machine once. Remember each project once. Keep every conversation private. Stop re-teaching agents what another session already learned.

01THE PROBLEM

Agent sessions start from zero. Two chats inside the same project share nothing, so deployment lessons, layout maps, and hard-won gotchas get re-derived — or pasted — every time. Global memory helps, but it mixes every project together. What is missing is a project brain: shared inside one project, invisible everywhere else.

🥇 One machine notebook
📓 One notebook per project
📝 Private notes per chat

02THE THREE LAYERS

L0 · MACHINE

🖥️ The machine

Environment, deployment pattern, secrets rules, budget caps. Nothing project-specific.

  • Host + toolchain facts
  • Shared deploy discipline
  • Safety + budget rules
  • Read by every session
L1 · PROJECT

📓 The project

What this project is, where things live, how it ships, lessons learned the hard way.

  • Goal + layout map
  • Deploy path + runbooks
  • Gotchas proven twice
  • Shared by that project's sessions only
L2 · SESSION

📝 The chat

Current task, scratch work, debug output. Private by construction.

  • Task + working notes
  • Sibling chats never see it
  • Fresh chat = clean slate, same L0+L1
  • Nothing auto-saves upward

03WORKED EXAMPLE — TWO PROJECTS, ONE PATTERN

Two services deploy to the same cloud account with the same discipline — loopback-only services, dashboard-managed ingress, secrets on the box, verify before presenting. The second project reuses the first project's notes instead of re-learning them.

📦 Project Atlas — web demoLive product demo with a Node server, static bundle, and an analytics sidecar.

Its brain records: loopback-only :8100 · ingress via dashboard · secrets at /secrets, never in repo · kill local canaries.
⇄
🔬 Project Beacon — research APIPython API with a pipeline runner and reverse proxy.

Its brain records its own stack — then adds one line: reuse Atlas deployment notes, read-only. Same discipline, no duplication, and Beacon can never edit Atlas.

04PROMOTION — HOW NOTES BECOME KNOWLEDGE

Session notes never become project knowledge by themselves. Promotion is explicit, gated, and auditable.

1 · ScratchA session learns something useful. It stays private by default.
→
2 · GateA check runs: is it durable? Are there secrets? Secrets are blocked, noise stays down.
→
3 · ApproveAn explicit approval appends it to the project brain with provenance.

05DESIGN PRINCIPLES

📖 Reads are freeEvery session loads machine + project notes at start. Broad to specific, budgeted, tiny.
🔒 Writes are gatedNothing promotes silently. Propose checks, approval writes, secrets refused.
🧱 Isolation by defaultTwo sessions in one project see identical shared notes and zero of each other's scratch.
🤝 Explicit sharingOne project may read another's brain for a genuinely shared pattern — read-only, never write across.
Honest limits. Memory files are kilobytes — they share knowledge, they do not shrink live conversation history. Long sessions with large subagent reports still need report caps, status-over-inbox reading, and timely compaction. Those are separate fixes.

06ADOPTING IT

  1. Write one machine file with environment, deploy discipline, and safety rules.
  2. Write one project brain per repo — goal, layout, deploy, gotchas — and have the harness auto-load it at session start.
  3. Add one memory rule to the agent instructions: read shared notes, keep scratch private, promote durable facts explicitly, never promote secrets.
  4. Prototype it with plain markdown files + a small gate script before building any plugin or database.
